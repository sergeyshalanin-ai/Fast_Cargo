Выгоды бизнеса
	1. Партнерство открывает выход на новые рынки и гарантирует десятикратный рост объемов бизнеса.
	2. Соответствие государственным и отраслевым стандартам в отношении перс данных клиентов и изоляция платежных контуров
	3. Стабильность при обработке высоконагруженных потоковых данных (IoT)
Базовая и целевая архитектура
	AS IS 
		Фронт-офис, ,бэк-офис, middleware
		Антиппатерны: 
			1. Размытие ответственности в слое BFF - нарушение паттерна SOLID
			2. Общая БД для всех сущностей в системе - единая точка отказа
			3. Низкая отказоустойчивость интеграционного шлюза
			4. Высокая связность кода
	TO BE 
		Через 3 месяца:
			Развернута отдельная БД (DWH) куда сливаются основные сущности и данные для сбора аналитики в ассинхронном режиме с помощью CDC 
		Через год:
			Каждый слой бэк-офиса преобразуется в отдельный продукт со своей БД:
				Заказы
				Доставка
				Финансы
				WareHouse
				Клиенты
			Взаимодействие между сервисами происходит через gRPC
			Есть единая точка доступа ApiGateWay которая маршрутизирует запросы мужду продуктами
			Подключены новые платежные сценарии через внешнего провайдера
			Персональные данные физически изолированы от операционной логики
			Взаимодейсвтие с датчиками оперативного контроля
			Внедрение EDI для обмена комерческими документами со всеми сетями холдинга
Область применения

		out-scope: остальные доработки продуктов
Ограничения и допущения
	Сроки:
		В рамках 3х месяцев необходимо реализовать только аналитику в реальном времени в DWH с задержкой не более 5 секунд. Реализация не должна затронуть исходный код легаси-монолита и создавать дополнительную SQL нагрузку на текущеую базу данных, чтобы исключить риски для операционной деятельности
		Через год необходимо демонтировать монолит и перейти на EDA
	Стандарты:
		Должно быть соответсвие требованиям 152-ФЗ в отношении персональных данных клиентов и ГОСТов РФ

Transition Architecture
				
	Уровень архитектуры: Данные			
	Текущее состояние (AS IS): Все запросы, также аналитические идут напрямую в операционную БД PostgreSQL
    Переходное состояние (через три месяца): Аналитические данный вычитываются асинхронно из WAL-логов без нагрузки на транзакционные таблицы
	Обнаруженный разрыв (gap) и локация изменений: Разрыв — отсутствие выделенного контура аналитики. Локация — слой хранения, развёртывание инстанса базы для чтения / CDC-инструмента.
	
	Уровень архитектуры: Приложения (Apps)
	Текущее состояние (AS-IS): Размытие ответсвенности в слое BFF, общая БД для всех сущностей системы, низкая отказоустойчивость интеграционного шлюза и высокая связанность кода
	Переходное состояние (через 3 месяца): Развернута новая БД DWH и в асинхронном режиме запрашивает WAL логи из общей БД без нагрузки на транзакционные таблицы
	Обнаруженный разрыв (gap) и локация изменений: Разрыв - отсутсвие выделеного контура аналитики. Локация - слой хранения, развертывание инстанса БД для чтения / CDC инструмента
	
	Уровень архитектуры: Инфраструктура (Infra)
	Текущее состояние (AS IS): не вижу описние текущей инфаструктуры
	Переходное состояние (через три месяца): Будут сформулированы инфаструктурным депаратаментом 
	Обнаруженный разрыв (gap) и локация изменений: требований по инфаструктуре не вижу и не было сформулированы от департаменты
Описание переходного состояния
	Операционные системы остаются без изменения. Чреез ETL/ELT процессы данные попадают в зону загрузки, где проходят первичный прием из иточников и базовую проверку. Далее данные загружаются в DWH. Над данным хранилищем строится BI 
7. Дорожная карта, риски и план перехода
	Пакеты работ и сроки: 
		1. Развернуть новое хранилище DWH - первый месяц
		2. Реализация ETL для получения данных из общей БД в DWH - первый месяц
		3. Сбор аналитики из нового DWH - 1 месяц
		4. Тестирование и пилот - 1 месяц
		Зоны ответсвенности: Новый продукт в части OLAP - отдельная команда разработки. Взаимодействие с командой целевого контура в части приема данных из единой БД. Развернуть новый продукт - ЛПР по инфраструктуре и эксплутации. Утверждения данных в новом продукте - ЛПР по безопасности и юристы. Поддержка и создание нового продукта - Технические ЛПР (Владелец продукта и арх комитет)
		Управление рисками и план отката -  Риски в части уровня загрузки данных - поторная загрузка без ключей дедуплкации после перезакпуска конвейера может перевести в дублях в отчетах. Синхронизация с внешними командами и требованиями снизит риск аварии - но не устранит его полностью.
		План отката: 
			1. Инициация - если SAL более 5 секунд или если по метрикам пошли дополнительная нагрузка на текущеую БД + либо проблема с данными - то запускается официальный план отката. Ответсвенный - дежурный ответсвенный за архитектуру
			2. Сетевой откат: Запуск стабильного IaC- скрипта из GIT - входящий трафик мгновенно возвращается на текущеую систему. Ответственный - сетевой инженер
			3. Консервация: Перевод новой базы данных в режим "Только чтение". Отключение ETL. Останаваливается запись в новых данных в проблемный контр DWH. Ответственный - Инженер эксплуатации
			4. Вывверка данных: Синхронизировать данные и понять проблему рассинхрона. Ответственный: Дата-инженер
			5. Проверка: QA-инженер - Проверка стабильности работы старой системы
		Критерии успешности и переключение: Нет рассинхрона в данных, SLA не превышет 5 секунд, нагрузка на старую БД не увеличилась. Мониторинг состояния в течении N времени.  Подтверждение об успешном переключении от всех стейкхолдеров
